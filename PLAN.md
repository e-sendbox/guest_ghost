# План разработки
## Предварительный дизайн
Приложение -игрушка, ищет подходящие варианты размещения для приведений. В базе приложения будет справочник домов (замки, подвалы, чердаки, где любят жить привидения). И база заявок от привидений с их именами и предпочтениями. 
Нюанс: база домов может заполняться любыми характеристиками, и пожелания привидений мы предусмотреть не можем. Так что поиск будем делать в несколько уровней
- косинусный коэффициент у нас будет динамический, в зависимости от уровня тревожности приведения от 0 до 1. 
- поиск домов свободных на желаемые даты - стандартный
- среди найденных ищем семантическим поиском по характеристикам в пределах персонального косинусного коэффициента.

Данные в домах будут делиться на 2 группы: время доступности номеров в доме, характеристики
Данные для приведений на 3 группы: крайняя дата вселения, тревожность, характеристики. 

Ориентировочный стек:
- LLM: облако Ollama (ollama.com) — deepseek-v4-flash:0731 (работает)
- эмбеддинги: ЛОКАЛЬНАЯ Ollama (localhost:11434) — облачных эмбеддинг-моделей в Ollama Cloud нет, проверено
- база данных: SQLite + sqlite-vec расширение. На большем масштабе постгре + pgvector 
- бэкенд: FastAPI (автодокументация Swagger, эндпоинты видны в браузере)
- фронтенд: NiceGUI (UI пишется на Python, как в проекте Rag) — выпадашки-автокомплиты, теги, таблицы без HTML/JS

Структура проекта (паттерн из Rag, логика течёт route → service → db/clients):
- main.py — диспетчер режимов (frontend / monolith), как в Rag
- config.yaml — модели, порт, api_url
- backend/ — FastAPI: db/ (schema, connection), clients/ (llm_client, embedding_client), services/ (hotel_service, ghost_service, search_service, enrich_service), routes/ (hotels, ghosts, search, ping)
- frontend/ — NiceGUI: main.py (страницы), api/client.py (HTTP-клиент к FastAPI), ui/ (формы домов, приведений, экран поиска, widgets)

**Подключение к моделям (проверено вручную)**

1. LLM — Ollama Cloud (облако), чат
- base url: https://ollama.com
- модель: deepseek-v4-flash:0731 (в облаке доступны deepseek-v4-pro:0813, glm-5.3, kimi-k3, qwen3.5:397b и др.)
- авторизация: Bearer OLLAMA_API_KEY из env
- эндпоинт: POST https://ollama.com/api/chat (stream) или /v1/chat/completions (OpenAI-совместимый)
- проверено: отвечает, температура 0.1, read_timeout ~90с

2. Эмбеддинги — ЛОКАЛЬНАЯ Ollama (WSL → localhost)
Ollama Cloud НЕ предоставляет эмбеддинг-модели:
- /api/embed на ollama.com → unauthorized (облако их не обслуживает)
- офлайн-модели (embeddinggemma, qwen3-embedding, all-minilm и т.п.) в списке облачных моделей отсутствуют

Поэтому эмбеддинг считаем локальной Ollama на localhost:11434 (уже запущена):
- модель: nomic-embed-text:latest — 768 dim, англ. (проверено, отвечает)
- модель: paraphrase-multilingual:latest — 768 dim, мультиязычная, русский поддержан (проверено) — РЕКОМЕНДУЕТСЯ для наших русскоязычных карточек
- эндпоинт: POST http://localhost:11434/api/embed, тело {"model": ..., "input": [...]}, ответ {"embeddings": [...]} (L2-нормализованные)

Шаблон подключения взят из проекта Rag (clients/ai_client.py): OllamaClient (облачный чат) + EmbeddingClient (локальные эмбеддинги), конфиг через yaml: embedding.model, embedding.url, llm.ollama.{base_url,model,api_key_env}.

3. ОБЛАЧНАЯ Jina (шаг 12, по умолчанию)
Для хостинга в облаке (Render и т.п.) локальную Ollama поднять негде — нужна облачная эмбеддинг-модель:
- сервис: Jina AI — https://api.jina.ai/v1/embeddings (POST, Bearer-авторизация)
- ключ: JINA_API_KEY из env (бесплатный, 10 млн токенов; проверено: отвечает, 768 dim)
- модель: jina-embeddings-v5-omni-nano — 768 dim (совпадает с БД FLOAT[768], миграция не нужна), мультиязычная
- ОБЯЗАТЕЛЬНО {"normalized": true} в запросе — sqlite-vec vec_distance_cosine требует L2-нормализованные векторы (Ollama нормализует сама, Jina — только по флагу)
- переключатель: config.yaml → embedding.type (cloud по умолчанию / local запасной), embedding.provider — сервис внутри типа (cloud → jina, local → ollama); проверка доступности при старте → стектрейс, если недоступен
- эндпоинт пересчёта старых векторов: POST /api/embedding/recalc (шаг 12)

## Модель данных

Два слоя в одной SQLite-базе:
1. Реляционные таблицы — жёсткие связи, поиск по датам.
2. Векторные таблицы (sqlite-vec) — виртуальные, хранят ТОЛЬКО `(id, embedding)`, умеют KNN-поиск.

Важно: автоматической связи между слоями нет. Синхронизацию (создание/изменение/удаление карточки → пересчёт эмбеддинга) держим в сервисном слое приложения.

### Реляционные таблицы (SQLite)

**hotel_characteristic** - словарь характеристик домов
- id (уникальный ключ)
- name (уникальное название: "освещение", "уровень шума"...)

**ghost_requirement** - словарь требований привидений (логика та же, что у hotel_characteristic, но свой словарь)
- id (уникальный ключ)
- name

**hotel_card** - карточка отеля (реляционная часть)
- id (уникальный ключ)
- name
- description
- characteristics - JSON-словарь тегов: {"освещение": "светло", "уровень шума": "низкий"} — у каждого отеля свой набор ключей, поэтому JSON, а не колонки
- restrictions - JSON (что нельзя)
- tags - JSON (свободные теги)


**hotel_rooms** - номерной фонд: номер либо занят, либо свободен с даты X и дальше (привидение вселяется навсегда)
- id (уникальный ключ)
- hotel_id
- free_date (дата = с какой даты свободен, по умолчанию с сегодня)
- при брони free_date сдвигается на конец брони; поиск: free_date >= желаемой даты
- reserved - false или true 

**ghost_request** - заявка приведения (одна заявка = одно приведение в поиске)
- id (уникальный ключ)
- name
- anxiety - от 0 до 1 (персональный косинусный коэффициент)
- requirements - JSON (требования приведения)
- preferences - JSON (пожелания)
- deadline_date (крайняя дата вселения)
- home_id INTEGER REFERENCES hotel_card(id)
- match_percent (пусто, пока дом не выбран/ забронирован)
- status - free (в поиске) / chosen (дом найден и показан) / reserved (забронирован)
- comment - общий комментарий по заявке 
- tags - JSON
- selection_hotel — объекты с полями: `home_id`, `name`, `free_date`, `match_percent`, `comment` (LLM, развёрнутый)
- free_date - дата-время перехода в статус «не заселен» (записывается при создании заявки, шаг 3)
- chosen_date - дата-время перехода в статус «подобран дом» (записывается при подборе, шаг 6; стирается при сбросе «никуда не заселять», шаг 5.1)
- reserved_date - дата-время перехода в статус «заселен» (записывается при брони, шаг 7)


### Векторные таблицы (sqlite-vec)

Виртуальные таблицы — содержат только `(id, embedding)`, нужные поля подтягиваются джойном с реляционными таблицами по id.

**hotel_card_emb**
- hotel_card_id
- embedding (FLOAT[768]) — эмбеддинг тегов карточки

**ghost_request_emb**
- ghost_request_id
- embedding (FLOAT[768]) — эмбеддинг тегов заявки




Поиск: KNN по векторной таблице с динамическим порогом (порог = f(anxiety)) → джойн с hotel_card → отсев по датам (hotel_rooms) → результат.

### Шаг0.2: Дистрибуция (деплой на Render)
**Цель** упаковать приложение для хостинга на Render (free-тир): зависимости, версия Python, подстановка env-переменных в конфиг, инструкция по панели. Код приложения НЕ меняется — только упаковка.

**Что делаем**

1. **`requirements.txt`** (корень) — продакшн-зависимости (playwright/pytest НЕ включаем — только для разработки):
```
nicegui==3.14.0
fastapi==0.139.0
uvicorn==0.44.0
requests==2.33.1
sqlite-vec==0.1.9
PyYAML==6.0.3
```

2. **`runtime.txt`** (корень) — `python-3.10.12` (та же версия, что локально; Render по нему выбирает Python для сборки).

3. **Подстановка env в конфиге** — `utils/env.py`: функция рекурсивно раскрывает `${VAR:-default}` во всех значениях config.yaml (сейчас `${APP_STORAGE_SECRET:-...}` — просто строка, код её не раскрывает). Вызывается при загрузке конфига (main.py / init.py). Тогда:
   - `config.yaml`: `port: ${PORT:-8080}` — на Render слушает `$PORT`, локально fallback 8080
   - `storage_secret: ${APP_STORAGE_SECRET:-...}` — начинает работать по-настоящему

4. **Ключи** — `JINA_API_KEY` / `OLLAMA_API_KEY` через env-переменные Render (панель сервиса → Environment). Код уже читает их из `os.environ` — менять ничего не нужно.

6. **Старт-команда** — `python main.py` (сам поднимет NiceGUI+FastAPI на `$PORT`).

7. **Инструкция по панели Render:**
   - Type: Web Service, Environment: Python
   - Build Command: `pip install -r requirements.txt`
   - Start Command: `python main.py`
   - Env: `JINA_API_KEY`, `OLLAMA_API_KEY` (секреты), при желании `APP_STORAGE_SECRET`
   - Free-тир: сервис засыпает через 15 мин без трафика, первый запрос после сна ~30-60с
   - БД не персистентная (файловая система пересоздаётся при деплое) → наполнение через «Предзаполнить» на DevINFO (5 домов + 5 заявок через API)

**Юнит-тесты**
```
tests/test_monolith.py — + тесты подстановки env:
  - ${VAR:-default} → default при отсутствии переменной
  - ${VAR:-default} → значение при наличии переменной
  - вложенные ключи конфига раскрываются рекурсивно
```

**Критерии успеха**
1. `pip install -r requirements.txt` в чистом venv → `python main.py` стартует
2. `PORT=10000 python main.py` слушает 10000 (не 8080)
3. Без env-переменных — fallback на дефолты из config.yaml
4. На чистой БД `init()` сам создаёт все 7 таблиц (включая vec0) — на Render ничего заливать не нужно
5. `pytest tests/` проходит

**Структура шага**
```
requirements.txt — продакшн-зависимости
runtime.txt — версия Python для Render (python-3.10.12)
utils/env.py — подстановка ${VAR:-default} в значениях конфига (рекурсивно)
config.yaml — port: ${PORT:-8080}
tests/test_monolith.py — + тесты подстановки env
```

**Статус** в плане, код не трогаем.

### Шаг2: Добавление жилищ (морда)
**Цель** Добавлять дома через морду (пока без пересчитывания векторов, только сохранение метаданных)

**Что делаем**
1. **Backend (монолит):** создаём `backend/` — FastAPI:
   - `main.py` — FastAPI-приложение, подключение роутов
   - `routes/hotels.py` — `POST /api/hotels` (создание дома), `GET /api/characteristics` (каталог)
   - `services/hotel_service.py` — `create_hotel()`: валидация, сохранение, каталог
   (схема БД и подключение — из Шага 0)
2. **Режим monolith:** `config.yaml → app.mode: monolith`; `main.py` — диспетчер монтирует FastAPI в NiceGUI (`app.mount("/api", ...)`), один процесс, один порт.
3. **Фронт:** `frontend/api/client.py` (из Шага 0) — методы `create_hotel()` и `get_characteristics()`.
4. **Попап «Добавить жилище»** (по кнопке на HomeDirect, по центру экрана), общий класс формы `form-popup`:
   - **Шапка** — заголовок «Добавить жилище» (светлая полоса по верхней, левой и правой границе), без кнопки «Отмена» и крестика.
   - **Инфо о доме:** название (обязательно), описание (обязательно, высокий текстбокс), характеристики (автокомплит: выпадашка из каталога + ввод своего + значение + «+» → чип «ключ: значение»), ограничения (через запятую, высокий текстбокс).
   - **Номерной фонд:** заголовок «Добавить в номерной фонд N место с ближайшей датой заселения» + спиннер количества (свои синие стрелки ▲▼) + календарь даты (readonly поле дд/мм/гггг, при клике по полю или иконке открывается русский календарь в сером стиле, навигация по месяцу/году не закрывает его) + «+» → сетка карточек «номер N» / «дата»; карточки удаляются красным крестиком.
   - **Футер** — кнопка «Сохранить» на всю ширину (длинная колбаса), светлая полоса по нижней, левой и правой границе.
5. **Валидация:** все поля непустые (название, описание, хотя бы одна характеристика, ограничения, хотя бы один номер) — пустые поля подсвечиваются красным плейсхолдером (без текстового сообщения), в БД не пишем.
6. **Чипы характеристик:** черно-синие с тонкой обводкой, серый текст, красный крестик удаления (как у номеров), без hover-подсветки; переиспользуемые (общий класс `.form-popup .q-chip`). Выбранные характеристики скрываются из выпадашки (защита от дубликатов); повторный ручной ввод перезаписывает значение.
7. **Сохранение одним скопом (транзакция):** `hotel_card` (name, description, characteristics JSON, restrictions JSON) → `hotel_rooms` (по карточкам, даты в формате ISO `гггг-мм-дд`) → `hotel_characteristic` (INSERT OR IGNORE — новые названия попадают в каталог). `asyncio.to_thread` для HTTP-вызовов (блокирующий requests в event loop NiceGUI даёт дедлок).
8. **Даты:** в интерфейсе всегда `дд/мм/гггг` (поле, календарь, карточки), в БД всегда ISO `гггг-мм-дд` (конвертеры `to_display`/`to_iso` в widgets.py; setup.py при установке нормализует старые записи).
9. **Логи:** факт сохранения дома (имя, число характеристик, число номеров), факт подгрузки каталога характеристик (количество).
10. Список домов на HomeDirect НЕ обновляем (отдельный шаг).

**Критерии успеха**
1. `python main.py` (mode=monolith) — один процесс, один порт, морда открывается
2. Кнопка «Добавить жилище» открывает попап по центру с фреймами
3. Автокомплит: выпадашка из каталога, можно вписать своё, пара «ключ: значение» добавляется чипом, чипы можно удалять, выбранные скрываются из выпадашки
4. Номерной фонд: спиннер меняет количество, «+» добавляет N карточек с датой, пусто → иконка, карточки удаляются
5. Календарь: открывается по клику на поле/иконку, русские месяцы и дни, навигация не закрывает, выбор дня подставляет дату
6. Пустые поля → красная подсветка плейсхолдеров, в БД не пишется
7. «Сохранить» → дом в `hotel_card`, номера в `hotel_rooms` (даты ISO), новые характеристики в `hotel_characteristic` (проверка через sqlite3)
8. Каталог характеристик подгружается при каждом открытии попапа
9. В лог записан факт сохранения с основной информацией

### Шаг4: Обогащение и эмбеддинг карточек
**Цель** подготовить карточки к семантическому поиску: LLM-нормализация тегов + эмбеддинг + сохранение в БД.

**Что делаем**

1. **Общий модуль обогащения** (`backend/services/enrich_service.py`):
   - получает на вход массив данных карточки (название, описание, характеристики/требования, ограничения/пожелания)
   - отдаёт в LLM (облачный deepseek-v4-flash) с задачей нормализовать текст: привести к нормальному виду, характеристикам с отрицанием подобрать прямую формулировку — результат: **список строк-тегов** (JSON-массив)
   - **проверка формата ответа**: если невалидный JSON/не массив строк — переотправляем максимум 3 раза с периодичностью 3 с
   - если всё равно НЕ ОК — функция возвращает ошибку вроде "LLM error"
   - если ОК — эмбеддим теги: **один вектор на карточку** (теги склеиваются в один текст → `EmbeddingClient.embed()`)
   - сохраняем теги (JSON-массив в `tags`) и эмбеддинг (в vec0-таблицу) в БД, возвращаем в функции статус вроде "success"

2. **Клиенты** (`backend/clients/`):
   - `llm_client.py` — облачный Ollama (deepseek-v4-flash), чат (паттерн из Rag: OllamaClient; read_timeout ~90с, не бесконечный)
   - `embedding_client.py` — локальная Ollama (paraphrase-multilingual, 768 dim), эмбеддинг (паттерн из Rag: EmbeddingClient)
   - конфиг: `config.yaml → llm.ollama` (base_url, model, api_key_env, temperature), `embedding` (url, model)

3. **Векторные таблицы (sqlite-vec)** — в `backend/db/schema.py`:
   - `hotel_card_emb (hotel_card_id INTEGER PRIMARY KEY, embedding FLOAT[768])`
   - `ghost_request_emb (ghost_request_id INTEGER PRIMARY KEY, embedding FLOAT[768])`
   - подключение расширения: `sqlite_vec.load(conn)` в `connection.py` (уже установлен пакет sqlite-vec 0.1.9)

4. **Прикрутка к карточке дома** (hotels_page.py):
   - после сохранения метаданных (POST /api/hotels), НО до закрытия формы
   - берём данные карточки (название, описание, характеристики, ограничения) → обогащение и эмбеддинг
   - смотрим результат обогащения, 
		- если success: по факту сохранения тегов и векторов — попап success «Данные карточки успешно сохранены», закрывается при клике на свободном месте экрана
		- если LLM error: при ошибке обогащения — попап error «Карточку дома не удалось обогатить, LLM не отвечает. Дом не доступен для заселения, но сохранен в базу данных. Передайте администратору <id карточки дома> для восстановления карточки.»

5. **Прикрутка к карточке заявки** (requests_page.py):
   - после сохранения метаданных (POST /api/ghosts), НО до закрытия формы
   - берём данные (требования, пожелания) → обогащение и эмбеддинг
   - смотрим результат обогащения, 
		- если success: по факту сохранения тегов и векторов — попап success «Данные карточки успешно сохранены», закрывается при клике на свободном месте экрана
		- если LLM error: при ошибке обогащения — попап error «Заявку не удалось обогатить, LLM не отвечает. Заявка недоступна для обработки, но сохранена в базу данных. Передайте администратору <id карточки заявки> для восстановления карточки.»

6. **Старые карточки** (уже в БД без тегов/эмбеддингов) — НЕ обогащаем в этом шаге, только новые при создании.

**Критерии успеха**

### Шаг5: Страница заявок 
**Цель** Показывать список заявок карточками: свёрнутый вид (базовая инфа), развёрнутый вид (список домов из selection_hotel). Заявки в статусе free корректно выводятся («не подобрано»).

### Шаг5.1: Перевыбор жилищ в ручном режиме
**Цель** позволить юзеру перевыбрать дом для заселения приведения (клик по «выбрать для заселения» у другого дома) и исключить заявку из подбора (красный кругляш «никуда не заселять»).

**Что делаем**

1. **Backend — перевыбор дома** (`ghost_service.select_home(config, request_id, home_id)`):
   - валидация: заявка существует, `home_id` есть в `selection_hotel` (иначе `ValidationError` → 400)
   - `match_percent` заявки берём из `selection_hotel` выбранного дома (процент только там и можно узнать)
   - `UPDATE ghost_request SET home_id = ?, match_percent = ? WHERE id = ?` — `status` не меняем (остаётся `chosen`)
   - лог: факт перевыбора (id, старый/новый дом)

2. **Backend — сброс заявки** (`ghost_service.reset_request(config, request_id)`):
   - `UPDATE ghost_request SET status='free', home_id=NULL, match_percent=NULL, selection_hotel='[]', comment=NULL WHERE id = ?`
   - лог: факт сброса (id)

3. **Backend — роуты** (`routes/ghosts.py`):
   - `POST /api/ghosts/{id}/select` (тело `{"home_id": N}`)
   - `POST /api/ghosts/{id}/reset`

4. **Фронт — клиент** (`client.py`): методы `select_home(request_id, home_id)`, `reset_request(request_id)`.

5. **Фронт — перевыбор** (`requests_page.py`):
   - **Надпись «выбран для заселения» становится кликабельной** (убираем некликабельность) — клик по ней тоже перевыбирает дом (по сути клик по любому дому = «выбрать для заселения»)
   - Клик по «выбрать для заселения» (в т.ч. у дома с match=0 — ручной выбор разрешён, юзер сам решает) → `select_home` → пересборка списка: выделение цветом, чип с процентом, надпись, данные в панели приведения («Выбран: <дом>», «Соответствие: X%»)
   - **Скролл-фокус:** после пересборки сохраняем `scrollTop` контейнера списка и восстанавливаем его (+ `scrollIntoView(block: 'nearest')` на карточке) — страница не пролистывается к началу, юзер видит, какой дом перевыбран
   - `asyncio.to_thread` для HTTP-вызовов

6. **Фронт — сброс** (`requests_page.py`):
   - Клик по красному кругляшу «никуда не заселять» (в шапке развёрнутого фрейма) → `reset_request` → пересборка списка: заявка становится `free`, раскрывашка неактивна (серая), дочерний фрейм исчезает
   - **`chosen_date` стирается** (NULL) — дата «подобран дом» больше не актуальна; `reserved_date` не трогаем (кругляша в статусе reserved нет, кейс нереалистичен)
   - Сброс возможен только при раскрытой заявке (кругляш в шапке фрейма) — юзер может не разворачивать дома и не перетыкать руками, система сама выбирает наилучший вариант из приемлемых
   - После сброса заявка попадёт в следующую подборку жилья (это явно прописано в тексте кругляша)

**Критерии успеха**
1. Клик по «выбрать для заселения» у другого дома → `home_id` и `match_percent` обновлены в БД, выделение и чип переехали на новый дом, данные в панели приведения обновились
2. Клик по «выбран для заселения» (выбранный дом) — тоже перевыбирает (кликабельная надпись)
3. Дом с match=0 можно выбрать вручную (ручной выбор разрешён)
4. Клик по красному кругляшу → заявка `free`, `home_id`/`match_percent`/`selection_hotel`/`comment` обнулены, раскрывашка неактивна
5. После перевыбора/сброса список не пролистывается к началу — скролл-позиция контейнера сохранена, фокус на карточке заявки
6. pytest: select (успех: home_id+match_percent обновлены; home_id нет в selection → 400), reset (status=free, поля обнулены)

### Шаг6: Подбор вариантов для приведений 
**Цель** Подобрать наилучшие варианты для каждого приведения по кнопке «Подобрать жилье».

**Что делаем**
1. **Кнопка «Подобрать жилье»** (на Guest Ghost) → запуск подбора.
2. **Выбор заявок:** `status = free`; если таких нет → попап «Приведений в поиске жилья не найдено».
3. **Цикл по каждой заявке:**
   - **Фильтр по датам (жёсткая отсечка):** дома, где `min(hotel_rooms.free_date) <= ghost_request.deadline_date` (самая ранняя дата заселения раньше дедлайна приведения).
     - если массив нулевой → `comment = "нет подходящих дат"`, `selection_hotel = []`, переход к следующей заявке.
     - если не нулевой → берём его. **Дома с неподходящими датами в selection_hotel не попадают вообще.**
   - **Векторное сравнение:** делаем по id выборку из sqlite-vec таблиц, высчитываем для каждого дома процент персонального сходства по нашей формуле. {home_id: match_percent}. **В selection_hotel попадают ВСЕ дома, прошедшие фильтр по датам, — и подходящие, и не подходящие по сходству (не подходящие получают match_percent = 0, из выборки не выпадают).**
   - **LLM-комментарий:** отдаём теги приведения + список домов с коэффициентом совместимости и тегами дома → LLM коротко комментирует каждый дом (что подходит приведению, что не подходит). **Для не подходящих домов (match_percent = 0%) LLM явно пишет, что не подходит.** Ошибка LLM → текст ошибки в `comment` объекта дома в selection_hotel.
   - **Запись:** `selection_hotel = [{"home_id", "name", "free_date", "match_percent", "comment"}]` (free_date = минимальная дата из hotel_rooms для дома, comment — развёрнутый от LLM), `home_id` = дом с наибольшим match_percent, **только если он > 0** (если у всех домов match_percent = 0 → `home_id` не пишем, NULL), `status = chosen` (всегда), **`chosen_date` = текущая дата-время** (дата перехода в «подобран дом»; при повторном подборе записывается заново). `comment` заявки при всех match = 0 **не пишем** (NULL) — «нет подходящих домов» убрано; LLM-комментарии в objects selection_hotel остаются.
4. **Бронирование не трогаем** — только подбор (номера не сдвигаем, free_date не меняем).
5. **Обновление морды** — после подбора пересобираем список заявок (карточки покажут варианты, жирные значения).


**Промпт для LLM**

```
# Goal: ты помогаешь привидению выбрать жильё. Прокомментируй каждый дом для конкретного приведения.

# Input
Приведение: <имя приведения>
Теги приведения: <tags из ghost_request.tags>
Список домов (по одному на строку):
1. <название дома> | сходство: <match_percent>% | теги: <tags из hotel_card.tags>
2. <название дома> | сходство: <match_percent>% | теги: <tags из hotel_card.tags>
...

# Rules
1. Для каждого дома дай короткий комментарий (1-2 предложения): что подходит приведению, что не подходит.
2. Учитывай теги приведения и теги дома, а также процент сходства.
3. Комментарий на русском, без пояснений и нумерации.

# OutputFormat
Верни ТОЛЬКО JSON-массив, где каждый элемент соответствует дому из списка по порядку:
[{"home_id": 1, "comment": "..."}, {"home_id": 2, "comment": "..."}]
```

**Формула релевантности жилья в соответствии с тревожностью приведения**

```
an = тревожность приведения (0..1) — это же минимальное косинусное сходство (порог)
cosine_sim = косинусное сходство векторов ghost_request_emb и hotel_card_emb (0..1)

Дом входит в варианты, если cosine_sim >= an.

match_percent (процент соответствия заявке):
  match_percent = max(0, (cosine_sim - an) / (1 - an) * 100)   # отрицательное → 0

При an >= 1 (паника): подходит только идеальное совпадение (cosine_sim = 1) → match_percent = 100.

Сортировка selection_hotel — по убыванию match_percent (лучший вариант первый).
```
**Формула на пальцах:**
- `an` — насколько приведение придирчиво. Тревожное (an=0.8) требует почти полного совпадения, спокойное (an=0.3) согласится на меньшее.
- `cosine_sim` — насколько дом похож на то, что приведение хочет (0 = совсем не похож, 1 = идеально).
- Дом получает больше 0% сходства, если похожесть не ниже придирчивости (`cosine_sim >= an`).
- `match_percent` — насколько дом **превосходит** минимальный порог приведения, в процентах:
  - дом ниже порога → 0% (не подошёл; всё, что ниже нуля — тоже ноль)
  - дом ровно на пороге → 0% (еле-еле подошёл)
  - дом идеально совпал → 100%
  - между ними — пропорционально.
- Пример: приведение с an=0.3, дом с cosine_sim=0.65 → (0.65-0.3)/(1-0.3)*100 = 50%. Дом с cosine_sim=0.3 → 0% (на пороге). Дом с cosine_sim=1 → 100%. Дом с cosine_sim=0.2 (ниже порога) → max(0, -14.3%) = 0%.
- Тревожное приведение (an=0.8): дом с cosine_sim=0.9 → (0.9-0.8)/(1-0.8)*100 = 50%. Только идеальный дом даёт 100%.

**Критерии успеха**
1. Кнопка «Подобрать жилье» запускает подбор; при отсутствии free-заявок — попап «Приведений в поиске жилья не найдено»
2. Заявки с неподходящими датами получают `comment = "нет подходящих дат"`, `selection_hotel = []`
3. В selection_hotel попадают ВСЕ дома, прошедшие фильтр по датам; match_percent считается по формуле (не подходящие = 0%, из выборки не выпадают)
4. LLM комментирует каждый дом (для не подходящих явно пишет, что не подходит); ошибка LLM → текст ошибки в comment объекта
5. `selection_hotel` заполнен (home_id, name, free_date, match_percent, comment), `home_id` = дом с макс. match_percent **только если он > 0** (иначе NULL), `status = chosen`; при всех match = 0 `comment` заявки не пишем (NULL), LLM-комментарии в objects остаются
6. Морда пересобирает список заявок после подбора
7. pytest: тесты подбора (мок cosine/LLM): фильтр дат, формула (0%/100%/промежуточные), запись selection_hotel, home_id при всех match=0 → NULL, comment при всех match=0 → NULL, ошибка LLM

### Шаг7: Заселение приведений
**Цель** Заселить приведений в подобранные дома, т.е. реализовать окончательную бронь через форму «Лист бронирования».

**Что делаем**

1. **БД (миграция):**
   - `schema.py` — в `hotel_rooms` добавить колонку `reserved INTEGER NOT NULL DEFAULT 0` (для новых БД)
   - `setup.py` — для существующей БД: `ALTER TABLE hotel_rooms ADD COLUMN reserved INTEGER NOT NULL DEFAULT 0` (с проверкой, что колонки ещё нет)
   - **При брони:** `hotel_rooms.reserved = 1`, `hotel_rooms.free_date = <фактическая дата-время заселения>` (дата нажатия «Заселить», та же, что в `reserved_date` заявки; номер исключается из будущих подборов фильтром `reserved = 0`)
   - **Привязка заявки к номеру НЕ нужна** (`ghost_request.room_id` не заводим): номера существуют только для подсчёта мест — можно ли заселить ещё кого-то

2. **Backend — `ghost_service.py`:**
   - `list_booking_candidates(config)` — заявки `status='chosen' AND home_id IS NOT NULL` (home_id обязателен), сгруппированные по дому:
     - дом: `name` (джойн `hotel_card`)
     - заявка: `name`, `anxiety`, `deadline_date`, `home_id`, `match_percent`
     - свободные номера дома для заявки: `reserved = 0 AND free_date <= deadline_date` заявки
   - `book_requests(config, bookings)` — массив `[{"request_id": N, "room_id": N}]`:
     - валидация каждой записи: заявка `chosen` + `home_id` не пуст; номер существует, `reserved = 0`, дата номера ≤ дедлайна заявки → иначе `ValidationError` → 400 (бэковая защита от конфликтов)
     - транзакция: заявка → `status = 'reserved'` + **`reserved_date` = текущая дата-время** (дата перехода в «заселен»); номер → `reserved = 1` + `free_date = '5026-01-01'`
     - лог: факт брони (количество, список request_id → room_id)

3. **Backend — роуты** (`routes/booking.py`):
   - `GET /api/booking/candidates` — список кандидатов
   - `POST /api/booking` (тело `{"bookings": [{"request_id": N, "room_id": N}, ...]}`)

4. **Фронт — клиент** (`client.py`): методы `get_booking_candidates()`, `book(bookings)`.

5. **Фронт — кнопка «Заселить в подобранное»** (уже есть визуальная, `requests_page.py`):
   - обработчик: грузим кандидатов
     - кандидатов нет → `ResultPopup` «Заселять некого, сначала подберите жилье»
     - есть → попап-форма «Лист бронирования» (стиль 1:1 `form-popup`, как у «Добавить жилище»/«Добавить заявку»)
   - `asyncio.to_thread` для HTTP-вызовов

6. **Фронт — форма «Лист бронирования»** (переиспользуем `ResultPopup`, `to_display`, стили `form-popup`/плашек/чипов):
   - **Шапка** — заголовок «Лист бронирования» (светлая полоса, как в формах)
   - **Группы по домам:** название дома (у левого края), под ним дочерние плашки приведений с отступом `padding-left: 24px` (`.booking-ghosts`) — визуально группируются под домом (в один дом могут заселить несколько приведений)
   - **Плашка приведения** — 3 колонки с вертикальными палочками (как на карточках заявок, колонки всегда рядом `nowrap`):
     - колонка 1: имя приведения (160px)
     - колонка 2: «Тревожность: X • Дедлайн приведения: <дд/мм/гггг> • Соответствие дома: X%» в одну строку, перенос по лейблам при сужении (как на карточках заявок); 0% — нормально (ручной перевыбор дома с нулевым соответствием), None → «не определен»
     - колонка 3 (фикс. 316px): выпадашка «Выбрать место» + кругляш `select-chip.nohome` (тот же, что в шапке заявок «никуда не заселять»: чёрный круг 40px, бордовая обводка, иконка `block`) с tooltip «Исключить из листа бронирования (вернуть в заявки)»
     - в выпадашке, если место уже выбрано, первым пунктом — «Очистить выбор» (сбрасывает выбор, место снова доступно другим заявкам в листе)
   - **Выпадашка «Выбрать место»:** в стиле автокомплита (синий треугольничек `arrow_drop_down`, серая выпадашка по ширине поля `booking-room-menu`), человеческий формат «Место N • дд/мм/гггг» (N = id номера из hotel_rooms); только свободные номера дома с датой ≤ дедлайна заявки
   - **Антиконфликт на уровне UI:** состояние формы хранит выбранные номера `{request_id: room_id}`; номер, уже выбранный другим приведением, НЕ предлагается в остальных выпадашках — конфликт невозможен
   - **Нет свободных мест** → в выпадашке disabled-пункт «Нет свободных мест»; заявка остаётся в листе (юзер решает крестиком)
   - **Валидация:** у заявок без выбранного номера — красная подсветка (как в «Добавить жилище»), «Заселить» не выполняется, в БД не пишем
   - **Крестик:** убирает заявку из листа и из массива формы; БД НЕ трогает (заявка остаётся chosen как была)
   - **Футер** — кнопка «Заселить» (как «Сохранить» в формах)

7. **Фронт — после «Заселить»:**
   - успех → закрыть форму, пересобрать список заявок, `ResultPopup` «Приведения заселены»
   - ошибка → `ResultPopup` с текстом ошибки

**Критерии успеха**
1. Нет кандидатов (chosen с home_id) → попап «Заселять некого, сначала подберите жилье»
2. Форма открывается: дома сгруппированы, плашки приведений с данными (имя, тревожность, крайняя дата)
3. Выпадашки предлагают только свободные номера (`reserved=0`) с датой ≤ дедлайна; формат «Место N • дд/мм/гггг»

5. Без выбранного номера — красная подсветка, в БД не пишем
6. «Заселить» → заявки `status='reserved'`, номера `reserved=1` + `free_date` = фактическая дата-время заселения (проверка через sqlite3)
7. Крестик убирает заявку из листа, БД не трогает (заявка остаётся chosen)
8. После заселения: форма закрыта, список пересобран, попап «Приведения заселены»
9. pytest: кандидаты (фильтр chosen+home_id, свободные номера с датой ≤ дедлайна), бронь (транзакция: status/флаги/free_date = фактическая дата заселения/reserved_date), валидации (нет номера, занятый номер → 400), инвариант: нет заявок с reserved_date без chosen_date

### Шаг8: Отчет по домам. 
**Цель** собрать отчет о заселенных приведениях по желанию пользователя (по заявкам / по домам).

**Что делаем**

1. **Миграция БД (setup.py):**
   - Стереть устаревшие записи: `comment = 'нет подходящих домов'` → NULL (старые заявки, созданные до правки шага 6) и `match_percent = 0` → NULL (для чистоты)
   - Пункт «все дома с 0% соответствия» из отчёта **убираем** — таких записей больше не будет

2. **Backend — `report_service.py` (новый):**
   - `build_report(config, mode, days)` — mode: `"requests"` | `"houses"`, days: период в днях (по умолчанию 1); **начало периода = сегодня минус N дней, 00:00**
   - **По заявкам:** выборка — **все незаселенные** (`status != 'reserved'`, независимо от даты создания: если кого-то не заселили хоть когда — он должен попасть в отчёт, чтобы было видно, что его не заселили, включая проблемные) **+ заселенные в периоде** (`status = 'reserved' AND reserved_date >= 00:00 начала периода`); **иерархия: сначала выборка массива, потом по массиву считаем поля**; группировка по **free_date**, только дни, где что-то происходило:
     - Воронка подбора: «Ждали заселения» (количество free_date в массиве), «Подобрано жилье» (количество chosen_date в массиве), «Заселены» (количество reserved_date в массиве)
     - Проблемные заявки: «нет подходящих дат» (количество заявок в массиве с comment = «нет подходящих дат»), "нет подходящих домов" (количество заявок, у которых в selection_home все дома с 0%)
   - **По домам:** дома из **той же выборки, что и по заявкам** (все незаселенные + заселенные в периоде), по `home_id` заявок (джойн отсекает заявки без дома), группировка по дому:
     - «Всего мест» — количество всех мест в доме из hotel_rooms
     - Воронка наполнения: «Свободно на начало» = `reserved=false` + `reserved=true & free_date > начала периода` (места забронированы во время периода, на начало были свободны); «Свободно на конец» = `reserved=false`
      - Аналитика дома: MAX % соответствия и AVG % соответствия считаются **по всем вариантам из `selection_hotel` заявок выборки** : берём все записи `selection_hotel` всех заявок выборки, группируем по `home_id`, оставляем только дома, присутствующие в выборке (по `home_id` заявок), и по полученному массиву процентов (с учётом всех нулевых значений) считаем максимум и среднее (округление до целых); «Динамика наполнения» = (free_date > начала периода)/Всего мест — доля мест, занятых за период, в процентах
     - **Все вычисления округляем до целых**
   - `routes/report.py`: `GET /api/report?mode=...&days=...`

3. **Фронт — клиент** (`client.py`): метод `get_report(mode, days)`.

4. **Фронт — попап «Отчет о заселениях»** (`layout.py`, заготовка уже есть):
   - **Выпадашка** в нашем стиле (синяя стрелочка, серая выпадашка, как «Выбрать место»): «Выбрать отчет» (по умолчанию не выбрана) → «по заявкам незаселенных на начало периода» / «по домам, выбранным за период»
   - **«Сформировать отчет <выпадашка>: последние [number_spinner, min=1, по умолчанию 1] дней.»**
   - **Плашка отчёта:** flex-контейнер, по высоте от «Сформировать за последние...» до конца формы над кнопкой «Сформировать»; пустая → иконка пустоты (например `insert_chart`); наполняется таблицей в нашем стиле (кастомная, как плашки, рядами)
   - **Кнопка «Сформировать»** — активировать (сейчас disabled); без выбранного отчёта — валидация (подсветка выпадашки), в БД не пишем

**Критерии успеха**

- У каждой вкладки — **свой адрес** (URL), чтобы можно было открыть её в новой вкладке браузера: `/guest_ghost`, `/homedirect`, `/devinfo`; `/` — редирект на `/guest_ghost`
- Фильтры передаются **query-параметрами** URL (переживают перезагрузку страницы)
- Формула фильтров заявок = **та же, что в отчёте (шаг 8)**: выборка `status != 'reserved' OR (status = 'reserved' AND reserved_date >= period_start)` + `free_date = date` (день строки отчёта) + доп. условие фильтра
- Фильтр «из заявки N» на странице домов показывает **только один дом** (на который кликнули)
- Фильтрация — **на сервере** (параметры в GET /api/ghosts, GET /api/hotels)

**Что делаем** 

0. **Рефакторинг: табы → отдельные адреса** (предпосылка для переходов):

1. Реализуем фильтры, поиски и сортировки. 
	- Механика работы должна быть устойчивой - после перезагрузки страницы фильтры не сбрасываются (query-параметры URL).

2. Для страницы "Заявки на заселение" - Переходы из отчета о заселении. Делаем кликабельными все цифры в отчете по заявкам. По клику открываем стр заявок на заселение в новой вкладке с соответствующим фильтром. В плашке с названием страницы слева от названия пишем в квадратных скобках название фильтра. 
	- ждали заселения в период с <дата>: `filter=waiting&date=<D>&period_start=<start>` — заявки выборки отчёта за день <D> (без доп. условия)
	- подобрано жилье в период с <дата>: `filter=chosen&date=<D>&period_start=<start>` — + `chosen_date IS NOT NULL`
	- заселены в период с <дата>: `filter=reserved&date=<D>&period_start=<start>` — + `reserved_date IS NOT NULL`
	- нет жилья с искомой датой в период с <дата>: `filter=no_dates&date=<D>&period_start=<start>` — + `comment = 'нет подходящих дат'`
	- нет подходящего жилья в период <дата>: `filter=no_homes&date=<D>&period_start=<start>` — + Python-фильтр: selection_hotel непустой, все match_percent = 0

### Шаг12: Облачная embedding-модель (Jina)
**Цель** Для хостинга приложения в облаке придется использовать облачную embedding-модель, а не локальную. Необходим переключатель в конфигах с локальной на облачную. Параметры подключения — через конфиг. **По умолчанию — облачный режим (Jina), локальный (Ollama) — запасной.**

**Договорённости**
- Ollama НЕ может быть облачным запасным вариантом (облачных эмбеддингов у неё нет). Оба режима — равноправные провайдеры одного интерфейса. Переключатель — `embedding.type` (local/cloud), провайдер — параметр внутри типа: `cloud` → `jina` (по умолчанию), `local` → `ollama` (запасной)
- Проверка доступности провайдера — при инициализации (шаг 0): недоступен/неверная размерность → стектрейс, приложение не стартует
- `normalized: true` для Jina обязателен (sqlite-vec `vec_distance_cosine` требует L2-нормализованные векторы; Ollama нормализует сама, Jina — только по флагу)

**Что используем**
- адрес модели (локальная): `http://localhost:11434` (Ollama, `/api/embed`)
- адрес модели (облачная): `https://api.jina.ai/v1/embeddings` (POST, Bearer-авторизация)
- ключ (облачная): `JINA_API_KEY` из env, бесплатный, 10 млн токенов (проверено: отвечает, 768 dim)
- название модели (локальная): `paraphrase-multilingual:latest` (768 dim)
- название модели (облачная): `jina-embeddings-v5-omni-nano` (768 dim)

**Что делаем**
1. `config.yaml` → `embedding.type`: `cloud` (по умолчанию) / `local` (запасной); `embedding.provider` — сервис внутри типа (`cloud` → `jina`, `local` → `ollama`); параметры подключения через конфиг для обоих режимов
2. `backend/clients/embedding_client.py` — рефакторинг: провайдеры `ollama` (local) / `jina` (cloud), один интерфейс `embed(texts) -> list[list[float]]`:
   - local: POST `{url}/api/embed`, `{"model", "input"}` (как сейчас)
   - cloud: POST `https://api.jina.ai/v1/embeddings`, Bearer `JINA_API_KEY`, `{"model", "input", "normalized": true}`, парсинг `data[].embedding`
3. Проверка доступности провайдера при старте (шаг 0): тестовый `embed(["test"])`, недоступен/неверная размерность → стектрейс, приложение не стартует
4. Эндпоинт пересчёта векторов для старых карточек (после смены провайдера): POST `/api/embedding/recalc` — по `hotel_card`/`ghost_request` с непустыми `tags`, пересчёт текущим провайдером
5. Проверка обоих режимов: добавление дома и заявки (реалистичные данные) → обогащение → `vec_length(embedding)` = 768 в vec0-таблицах

**Критерии успеха**
1. `type=cloud` (default, provider=jina): обогащение работает через Jina API (ключ из env), 768 dim
2. `type=local` (запасной, provider=ollama): обогащение работает через локальную Ollama, 768 dim
3. При старте недоступный провайдер или неверная размерность → стектрейс, приложение не стартует
4. POST `/api/embedding/recalc`: векторы старых карточек пересчитаны (по непустым tags)
5. pytest: тесты клиента (мок): ollama-запрос, jina-запрос (Bearer, `normalized: true`), парсинг ответа Jina, recalc
6. Регрессия: pytest 45 + Playwright 74

**Структура шага**

### Шаг13: Страница Dev info 
**Цель** показать сопроводительную документацию сервиса прямо в приложении.

**Договорённости**
- Дерево PLAN.md — аккордеон: вложенные раскрывающиеся блоки, клик по заголовку раскрывает/сворачивает детей; по умолчанию всё свёрнуто
- «Предзаполнить» — добавление через API-эндпоинты (POST /api/hotels, /api/ghosts) + обогащение: те же механизмы, что и формы (валидация, каталог, LLM-теги, эмбеддинг) — «через UI» в смысле «через те же механизмы»

- **Обогащение — через HTTP-эндпоинт `POST /api/enrich`** (вариант Б): оборачиваем `enrich()` в эндпоинт, **формы «Добавить жилище/заявку» переводятся на HTTP-вызов** (вместо `asyncio.to_thread(enrich, ...)`), `seed_demo()` использует тот же эндпоинт — единый механизм, все операции через API

# Короткие инструкции 

## Процесс оператора бюро 
**На стр Dev INFO можно полностью очистить (кн. "Обнулить БД") и наполнить (кн. "Предзаполнить") базу демонстрационными данными: 5 заявок и 5 жилищ** 

1. Добавить жилище для заселения: стр. HOMEDIRECT - кн. "Добавить жилище" -> увидеть дом в справочнике.  
2. Добавить заявку от приведения: стр. GUEST GHOST - кн. "Добавить заявку" -> увидеть заявку в статусе "не заселен" в справочнике. 
**на операциях добавления LLM-нормализуем данные заявок и жилищ в облако тегов, эмбеддим, сохраняем в бд теги и вектора.**

3. Подобрать жилище для приведений: стр GUEST GHOST - кн. "Подобрать жилье" -> увидеть заявку в статусе "подобран дом"
**Будут взяты все заявки в статусе "не заселен". На операции подбора для каждого приведения: отсекаем дома не подходящие по дате, для всех оставшихся вычисляем процент совместимости дома с запросом и тревожностью приведения. Подробная формула в "Плане разработки" - "Функциональностях" - шаге6**

4. Развернуть карточку заявки кликом, выбрать другой дом для приведения -> увидеть перезапись выбранного дома.
**Я разрешила заселять приведений в дома с нулевой совместимостью, т.к. вывожу полные данные о запросе приведения, свойствах дома, резолюцию LLM и вычисленный % совместимости. Также можно отбросить заявку в статус "не заселен", обработать повторно, когда появятся новые дома** 

5. Заселить приведений: стр GUEST GHOST - кн. "Заселить в подобранное" -> выбрать места для приведений -> увидеть заявку в статусе "заселен". 
**Конфликт мест невозможен, т.к. предлагаются только доступные номера, не назначенные др. приведениям. Так оператор, глядя на тревожность приведения и совместимость дома, может сам выбрать, кому выдать дефицитное место. Также можно выбросить заявку из листа заселения, она останется в статусе "подобран дом".**

6. Посмотреть отчеты о заселении: икона на вкладке GUEST GHOST. 
- отчет по заявкам собирает заявки всех незаселенных на начало периода. Если заявка была создана до начала периода, но приведение не заселили - оно попадает в отчет. Все значения в отчете кликабельны. 
- отчет по домам собирается по выбранным за период домам. Это заявки в статусах "подобран дом" и "заселен"

7. Посмотреть переполненные дома: стр. HOMEDIRECT - фильтр "Доля занятых мест".
